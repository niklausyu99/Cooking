# 家庭使用流程、卡片管理与同步审查

日期：2026-10-20。范围：当前 Little Basket 独立 HTML、家庭 RPC SQL、既有浏览器测试；合并此前待发布的「默认／最新添加」菜谱排序。保留现有奶白、橄榄绿、柔和砖红、中文字体和食物插画。

## 证据与边界

本报告是开发者模拟家庭用户与 UI/UX 专家的走查，不是真实家庭成员访谈，也不虚构满意度、用户原话或线上使用统计。使用隔离 Chromium 存储、本地 HTTP 服务、移动视口和可控的 revision/CAS RPC 替身。真实生产家庭数据未读写；未调用真实家庭连接码。实际 iPhone/Safari、Android 安装及真实 Supabase 双设备网络仍需家人设备验收，不能以 Chromium 视口或模拟 RPC 冒充。

使用项目 `mobile-kitchen`、`design-taste-frontend` 的 app-screen 规则、`frontend-design` 的已有风格保持与截图自检；主方案沿用项目原有方向，不抽取新营销页面风格。未调用或声称调用设计子代理。

## 家庭用户视角：模拟流程与反馈

1. 在菜谱选两道共用番茄的菜，清单合并用量；切换人数换算，家里已有的食材进入略过区。保留单次选菜直接生成清单的成熟流程。
2. 在选购搜索、切换一／二／三列、加入额外物品，浮篮预览并写备注。购买确认仍集中在完整清单；预览不重复采购操作。
3. 在清单打钩购买，库存和购买记录同步产生；取消误勾与删除误记购买保留既有回退逻辑。新一趟只清采购，不清库存与历史。
4. 长按或点「···」改物品名称，旧名称仍可作为别名搜索；重名阻止保存，关联的菜谱、历史和插画沿原 ID 继续用。删除卡片时说明影响和恢复位置。
5. 删除已选的内置菜谱，与另一道菜共用的番茄、单独选购、家中库存、购买历史均保留；刷新并模拟旧目录升级，菜谱不补回。带变体的菜谱删除不留下无效变体选择。
6. 添加并编辑自家菜谱，默认餐罩保留；删除自建菜谱，不删它曾创建的食材。开发者补专属图片时，通过 ID 匹配覆盖默认图，不触碰业务实体。
7. 第二设备接收菜谱删除、物品改名和隐藏。离线删除后重开再联网可续传；另一台仍有旧菜谱且发生新修改时，出现冲突而非静默覆盖。

**正向判断（模拟，非真实用户反馈）：** 底部四模块、搜索、菜谱一键转清单、重复食材合并、浮篮备注与删除、手动余量、购买后记库存、独立设置入口都能减少操作，保留它们；不增加新的全局工具栏或强制教程。

**负向判断与已处理：**

- 仅有长按对不熟悉手机操作的家人不可发现：物品名称旁和菜谱图右上增加「···」入口；按钮至少 44 px。
- 物品编辑若复制成新 ID 会断开历史：只改原实体名称／分类，旧称留作别名，不开放图标字段。
- 内置菜谱删除若只从数组移除，下次启动必然恢复：保存独立删除记录并在种子合并中跳过。
- 物品被其他菜谱和历史引用，直接删实体会损坏引用：仅隐藏选购卡片并从本趟移除；确认文字明确说明，设置可恢复。恢复不自动替用户重新采购。
- 调料罐或米饭不能代表任意新增内容：改用中性纸袋／餐罩。
- 同步若在用户打字或确认删除时替换状态，会令决定失去上下文：延后接收，保留本机编辑；检测到两边变更仍要求明确选择。远端删除正在阅读的菜谱时，收起详情并提示；仅改名则刷新详情而保留阅读位置，避免失效的编辑／选菜入口。
- 冲突原摘要不显示菜谱，只有删除菜谱时两份摘要可能看似相同：补入菜谱总量和已删除数量。

## UI/UX 专家视角

保持原层级：食物插画 → 名称 → 库存状态 → 加入清单；管理入口为次级。市场名称行采用可点击文字和小号省略号，不增加独立大按钮行；菜谱管理入口位于插画右上，已选标记移到右下避免覆盖同一位置。操作弹窗使用原有 dialog、表单、边距，删除动作以柔和砖红区分，确认按钮写「删除菜谱／删除物品」。

指南用原生 details 分主题，14 px 正文、15 px 小标题，44 px 展开目标，默认不弹出。保留现有色彩与字体；不以设计工具对奶白配色的通用警告为由重做用户指定风格。

待后续真实反馈验证的建议（未擅自开发）：若家人经常同时改不同条目，再评估逐项合并；如果找「···」仍困难，再做一次性就地提示；若家里有低视力使用者，再评估全局字号设置。当前先不增加按钮、账户或复杂教程。

## 数据与同步结论

- SQL `sync_family_kitchen` 在同一条原子 UPDATE 中匹配 `expected_revision`，失败返回 PT409；读接口按 revision 省略未变化的状态。没有发现必须替换这套机制的证据。
- 当前是整份家庭状态 CAS，并非自动逐条合并。并发新增或修改不同项目也可能需要选择一份；未选择时两份各自保留、不覆盖云端。明确选择后下载将被替换的 JSON，用户可以取回另一份内容。此边界在指南说明。
- 删除、隐藏和文字编辑标记均是 version 1 可选字段，旧备份补默认值，导入验证检查唯一性／引用，首次本机迁移计入有效改动；不需要修改数据库或重跑初始化 SQL。
- 不改 RPC 权限、家庭链接、令牌或生产数据。默认 SVG 和图片定义仅在 HTML，家庭记录不携带图片数据。
- 删除记录阻止新版目录补回。主动导入删除前的旧备份、或明确选择旧设备整份记录属于用户确认的替换，并非静默恢复；并发时应查看摘要、保留下载副本。发布后旧窗口需刷新以使用新的删除逻辑。

## App-screen 截图复审

最终 inspector 运行于 1440 / 768 / 390 px，0 FAIL / 3 WARN；十张截图与上一轮已逐张目视检查的截图字节相同。另行检查 390 px 的管理菜单、砖红删除确认、默认餐罩、默认纸袋、物品编辑和指南；320 px 的边界与 44 px 目标由浏览器操作断言覆盖。

按 app-screen 复审的七个问题逐项回答：

1. 主问题仍是「今天要补什么」，食物和物品名优先，加入清单为主操作；编辑／删除是次级管理，没有挤进主操作行。菜谱排序沿用现有行，默认／最新添加不占一整排大选择框。
2. 各卡片仍沿原网格边缘对齐；指南、编辑和确认弹窗使用一致左右内边距。大屏双列较疏是既有用户选择，允许切成三列，不擅自改其列数。
3. 绿色用于已加入、家里有和主操作；柔和砖红用于删除与用完。默认插画沿用纸袋暖褐和叶绿；没有引入新的主题色或装饰图表。
4. 菜篮图按清单物品总数，角标按待买数。删除菜谱后共享食材重新合并，勾选和来源引用由现有 `mutate` 整理，保留库存／历史；状态与数量回归通过。
5. 空篮保留 0 样，未知库存仍为待确认，未记录余量不伪造百分比；图标旁的数量表示待买，不表示历史购入。
6. 本轮无图表／图例；省略号作为管理控件，菜谱已选标记换到右下，与右上管理入口分开。删除按钮同时靠文字和砖红区分。
7. 手机保留底部四入口，浮篮随滚动收窄，管理菜单和指南在当前屏幕内；表单输入 16 px，44 px 目标支持单手点击和键盘。

三个 WARN 的处置依据：奶白配色由用户明确要求保留；既有目录次级提示较小，主名称／关键库存仍有层级，新指南正文为 14 px，本轮不重设全局字号；54 张目录卡片本来是滚动选购目录，有搜索、分类和列数控制，不把数据强挤成大屏仪表盘。`--allow button-fx` 仅沿用真实悬浮篮子的投影，非给普通静止卡片新增阴影。静态 lint 的四处阴影告警来自既有菜单、浮层与浮篮交互。

额外尝试直接以 `file://` 打开独立 HTML，但当前托管 Chromium 的管理员策略返回 `ERR_BLOCKED_BY_ADMINISTRATOR`；没有绕过策略。独立文件的本地 HTTP 操作和 PWA 断网重新载入已单独测试，不能把它写成真实本机文件打开已验收。
